## 1. Purpose

PatchShuttle is a local Python library and command-line tool for building,
auditing, modifying, testing, formatting, and recovering software projects
through small, controlled jobs generated by ChatGPT or other AI services.

The normal workflow is manual and stepwise:

1. The user gives an AI a project handoff or the latest PatchShuttle log.
2. The AI returns one declarative `.psh.yaml` job.
3. The user places the job in the project and reviews the execution plan.
4. PatchShuttle validates and applies the job locally.
5. PatchShuttle optionally lints changed HTML, runs checks, then isort and
   Black, then repeats the checks.
6. PatchShuttle creates a timestamped log for the user to return to the AI.
7. The next job is created only after the previous result is understood.

PatchShuttle must also support starting in an empty directory and building a
new project through a sequence of jobs.

## 2. Product principles

### 2.1 AI describes intent, local policy grants authority

An AI job may request actions and checks. It may not relax local security,
backup, confirmation, formatting, or rollback policy.

### 2.2 Complexity stays inside PatchShuttle

The AI-facing format must contain only project-specific intent. Repeated logic
for path validation, backups, logging, rollback, testing, formatting, error
handling, and idempotency belongs to PatchShuttle.

### 2.3 Safe failure is more important than partial success

A validation, policy, action, lint, check, or formatting failure stops the job.
PatchShuttle then restores the files covered by its transaction unless the user
explicitly selected `--keep-changes`.

### 2.4 Recorded attempts are auditable

Every execution attempt and every validation or planning failure after
workspace resolution creates a human-readable UTF-8 log with stable status
codes and a compact AI handoff section. Successful standalone `validate` and
`plan` commands remain artifact-free. A workspace-discovery failure has no
resolved workspace in which to write a log.

### 2.5 No hidden remote service

PatchShuttle itself does not call an AI API, upload project data, or require a
cloud account. The user manually transfers jobs and logs between the local
project and an AI service.

### 2.6 PatchShuttle is not a security sandbox

Built-in path and policy checks reduce accidental damage. They do not make
AI-generated source code trustworthy. Project checks such as pytest execute
project code and may have effects outside PatchShuttle's file transaction.

## 3. v0.1 scope

PatchShuttle v0.1 includes:

- initialization of existing and new projects;
- a compact versioned YAML protocol;
- `audit`, `patch`, and `verify` jobs;
- a public Python API using the same job and action models;
- read-only audit actions;
- guarded text-file creation and modification actions;
- unified diff application for existing text files;
- built-in Python, pytest, unittest, and Django check profiles;
- user-defined check profiles stored in local configuration;
- execution planning and interactive approval;
- project-local backups and rollback;
- automatic isort and Black formatting of changed Python files;
- optional djLint lint-only checks for changed HTML files;
- initial and final checks;
- timestamped logs, snapshots, and AI handoffs;
- Windows and Linux support;
- operation with or without Git.

## 4. Explicit non-goals for v0.1

The first release does not include:

- a graphical interface;
- direct ChatGPT, OpenAI API, or other AI integrations;
- remote project execution;
- automatic dependency installation;
- arbitrary shell snippets supplied by a job;
- executable Python job files as the default AI format;
- file deletion, move, or rename actions;
- regular-expression replacement;
- binary-file creation or modification;
- downloading files from the internet;
- automatic Git commits, branches, or pull requests;
- Git repository initialization;
- plugin discovery;
- cryptographic job signing;
- complete operating-system isolation;
- automatic backup cleanup.

## 5. Terminology

| Term | Meaning |
| --- | --- |
| Workspace | The project root managed by one PatchShuttle configuration. |
| Job | One versioned YAML or Python API description of requested work. |
| Action | One audit or change operation inside a job. |
| Check | A controlled verification profile executed by the runner. |
| Policy | Local rules that an AI job cannot weaken. |
| Plan | A validated preview of files, actions, checks, and consequences. |
| Run | One attempt to validate or execute a job. |
| Transaction | The set of declared files protected by one backup manifest. |
| Handoff | A compact log intended to be returned to an AI. |

## 6. Architecture

PatchShuttle has three public-facing layers:

```text
Python API
    |
Job model, planner, runner, actions, checks
    |
YAML adapter and CLI
```

YAML jobs and Python API jobs must produce the same internal `Job` model and
must use the same planner, policy checks, action implementations, backup logic,
runner, and result model.

Core components:

- workspace discovery and configuration;
- job parsing and schema validation;
- action and check registries;
- path and policy validation;
- plan generation;
- backup manifests;
- transactional action runner;
- check runner;
- isort and Black adapters;
- rollback engine;
- project registry;
- structured human-readable logging;
- CLI and public Python API.

## 8. Workspace initialization

### 8.1 Existing project

```bash
cd existing_project
patchshuttle init
```

### 8.2 New project

```bash
mkdir new_project
cd new_project
patchshuttle init --new-project
```

`--new-project` accepts an empty directory or a directory containing only a
`.git` directory and operating-system metadata. A non-empty project must use
normal `init`.

Running `init` again must not overwrite user-edited configuration, jobs, logs,
protocol guides, or backups.

### 8.3 Explicit workspace routing

Workspace-aware CLI commands accept a global option before the command:

```bash
patchshuttle --workspace PATH COMMAND [ARGS]
```

An explicit path is loaded as the exact workspace root. Without it,
PatchShuttle discovers the nearest initialized current directory or parent. If
implicit discovery fails, the CLI may inspect at most 100 direct child entries
and report at most three valid initialized candidates. Candidate discovery is
advisory and never selects or executes against a child automatically. Job-file
arguments remain relative to the process current directory.

### 8.4 Generated structure

```text
patches/
|-- inbox/
|-- applied/
|-- failed/
|-- logs/
|-- backups/
|-- state/
|   |-- registry.json
|   `-- run.lock
|-- examples/
|-- patchshuttle.toml
|-- AI_GUIDE.md
|-- PATCHSHUTTLE_PROTOCOL.md
`-- patchshuttle.schema.json
```

The `patches` directory is protected from normal change actions. PatchShuttle
itself may update its state, logs, archives, backups, and generated guides.

### 8.5 Project identity

Initialization creates a project identifier with this form:

```text
PSH-8F41C2A73D905E61
```

The identifier format is `PSH-` followed by sixteen uppercase hexadecimal
characters generated from a cryptographically secure random source.

Every job must contain the matching `project_id`. A mismatch stops execution
before any file is changed.

The identifier remains stable if the project directory is moved.

## 9. Local configuration

The canonical configuration path is:

```text
patches/patchshuttle.toml
```

The generated default is conceptually equivalent to:

```toml
[project]
project_id = "PSH-8F41C2A73D905E61"
origin = "existing" # existing | new

protected_paths = [
  ".git/**",
  ".env",
  ".env.*",
  "patches/**",
  ".venv/**",
  "venv/**",
  "node_modules/**",
]

protected_path_exceptions = [
  ".env.example",
  ".env.sample",
  ".env.template",
]

ignored_paths = [
  ".git/**",
  "patches/backups/**",
  "patches/logs/**",
  "patches/state/**",
  ".venv/**",
  "venv/**",
  "node_modules/**",
  "**/__pycache__/**",
  ".pytest_cache/**",
  ".mypy_cache/**",
  ".ruff_cache/**",
]

[execution]
confirm = true
auto_rollback = true
allow_keep_changes = true
default_timeout_seconds = 300
max_job_bytes = 2000000
max_actions = 100
max_single_file_bytes = 1000000
max_command_output_bytes = 2000000
max_inventory_entries = 50000
max_inventory_bytes = 1000000000

[formatting]
enabled = true
order = ["isort", "black"]
scope = "changed_python_files"
rerun_checks = true

[linting.html]
enabled = false
tool = "djlint"
profile = "html"
scope = "changed_html_files"
ignore = []

[logging]
timezone = "local"
include_command_output = true
redact_known_secrets = true

[checks]
require_at_least_one_for_patch = true
```

Configuration values are user policy. A YAML job cannot override:

- project root or project ID;
- protected paths, protected-path exceptions, or ignored paths;
- confirmation requirements;
- backup and rollback policy;
- formatting order;
- HTML lint enablement, profile, ignore rules, or scope;
- command allowlists;
- size or output limits;
- shell execution policy.

PatchShuttle must use `tomllib` where available and the `tomli` compatibility
package on Python 3.10.

## 10. YAML job protocol

### 10.1 Canonical extension

```text
.psh.yaml
```

`.psh.yml` and JSON jobs are not accepted in v0.1.

### 10.2 Common top-level fields

```yaml
protocol: 1
project_id: PSH-8F41C2A73D905E61
id: PATCH-001
kind: patch
title: Add email validation
description: Add guarded validation and tests for client email addresses.
actions: []
checks: []
```

Required fields:

- `protocol`;
- `project_id`;
- `id`;
- `kind`.

Conditional fields:

- `actions` is required and non-empty for `audit` and `patch`;
- `checks` is required and non-empty for `verify`;
- `checks` is required and non-empty for `patch` under the default local
  policy.

Optional fields:

- `title`;
- `description`.

Unknown top-level or action-level fields are rejected.

### 10.3 Job ID

The job ID must match:

```text
^[A-Z][A-Z0-9_-]{2,63}$
```

Examples:

```text
PATCH-001
EMAIL_VALIDATION_002
FIX-MANAGER-TIMEOUT
```

The project registry stores the job ID, normalized job hash, run history, last
status, and rollback status.

Rules:

- same ID and same hash after successful completion returns
  `ALREADY_APPLIED`;
- same ID and different hash returns `PATCH_ID_CONFLICT`;
- a failed job with the same ID and same hash may be retried;
- a rolled-back job with the same ID and same hash may be run again.

### 10.4 YAML safety rules

The parser must:

- use safe YAML loading;
- reject custom YAML tags;
- reject anchors and aliases;
- enforce the configured input-size limit before parsing;
- reject duplicate mapping keys;
- validate the parsed value with typed models;
- reject unknown fields;
- produce errors with a YAML field path and stable error code.

### 10.5 Action syntax

Each list entry contains exactly one action name:

```yaml
actions:
  - read:
      path: src/example.py

  - search:
      path: src
      text: "example"
```

The runner assigns stable sequential IDs such as `action_001`. AI jobs do not
need to generate action IDs.

## 11. Job kinds

### 11.1 `audit`

An audit job may contain only read-only audit actions. It creates no backup and
does not run formatters.

```yaml
protocol: 1
project_id: PSH-8F41C2A73D905E61
id: AUDIT-001
kind: audit
title: Inspect the initial project structure

actions:
  - tree:
      path: .
      depth: 4

  - read:
      path: pyproject.toml
      start_line: 1
      end_line: 200

  - search:
      path: src
      text: "TODO"
```

### 11.2 `patch`

A patch job contains one or more guarded change actions and, by default, one or
more checks.

```yaml
protocol: 1
project_id: PSH-8F41C2A73D905E61
id: PATCH-001
kind: patch
title: Add a greeting function

actions:
  - create_file:
      path: src/example/greeting.py
      content: |
        def greet(name: str) -> str:
            return f"Hello, {name}!"

checks:
  - compileall:
      paths: ["src"]
```

### 11.3 `verify`

A verify job contains no change actions. It runs controlled checks and creates
a log.

```yaml
protocol: 1
project_id: PSH-8F41C2A73D905E61
id: VERIFY-001
kind: verify
title: Run the client test suite

checks:
  - pytest:
      paths: ["tests/test_clients.py"]
      args: ["-q"]
```

## 12. Audit actions

All audit actions must respect protected paths, ignored paths, file-size limits,
and log-output limits.

### 12.1 `tree`

Fields:

- `path`: relative directory, default `.`;
- `depth`: integer from 1 to 10, default 4;
- `max_entries`: integer, default 500;
- `include_hidden`: boolean, default false.

Output includes relative paths and entry types. It does not include file
contents.

### 12.2 `read`

Fields:

- `path`: required relative text-file path;
- `start_line`: positive integer, default 1;
- `end_line`: optional inclusive line number;
- `max_bytes`: optional value not exceeding local policy.

The action rejects binary files and protected paths. Output includes numbered
lines and a truncation marker when a limit is reached.

### 12.3 `search`

Fields:

- `path`: relative file or directory, default `.`;
- `text`: required literal string;
- `glob`: optional file glob;
- `case_sensitive`: boolean, default true;
- `max_results`: integer, default 200.

v0.1 search is literal. Regular-expression search is not supported.

### 12.4 `find_files`

Fields:

- `path`: relative directory, default `.`;
- `glob`: required glob;
- `max_results`: integer, default 500.

### 12.5 `file_info`

Fields:

- `path`: required relative path.

Output may include type, byte size, encoding result, newline style, executable
bit where available, and last modification time.

### 12.6 `hash`

Fields:

- `path`: required relative file path;
- `algorithm`: only `sha256` in v0.1.

### 12.7 `git_status`

The action accepts no fields. If Git or `.git` is unavailable, the action
returns `NOT_AVAILABLE` without failing the audit job.

### 12.8 `environment`

The action accepts no fields. Output is limited to non-secret metadata:

- operating system;
- Python implementation and version;
- PatchShuttle version;
- workspace project ID;
- availability and versions of Git, pytest, isort, and Black;
- current working directory with user-home components redacted where possible.

It must not enumerate environment-variable values.

## 13. Change actions

All change actions operate only on text files inside the workspace root. They
must be fully planned before any write occurs.

### 13.1 Shared path rules

- paths are relative to the workspace root;
- absolute paths are rejected;
- `..` traversal is rejected;
- URL paths are rejected;
- protected paths are rejected;
- a target or existing parent that is a symbolic link is rejected;
- path comparison uses resolved paths and platform-appropriate case behavior;
- the root and `patches` directory cannot be change targets.

### 13.2 `create_directory`

Fields:

- `path`: required relative directory.

Behavior:

- absent directory: create it and record it in the manifest;
- existing directory: return `NO_CHANGE`;
- existing non-directory at the path: fail;
- rollback removes the directory only if the job created it and it is empty.

### 13.3 `create_file`

Fields:

- `path`: required relative file path;
- `content`: required text;
- `encoding`: optional, default `utf-8`;
- `newline`: `lf` or `crlf`, default `lf`.

Behavior:

- missing parent directories are created and recorded automatically;
- absent file: create it atomically;
- existing file with identical normalized bytes: return `NO_CHANGE`;
- existing file with different content: fail;
- files larger than local policy are rejected before writing.

### 13.4 `replace_exact`

Fields:

- `path`: required existing text file;
- `old`: required non-empty exact text;
- `new`: required replacement text;
- `expected_count`: positive integer, default 1.

Behavior:

- preserve detected encoding and newline style;
- count exact occurrences before changing the file;
- apply only when the count equals `expected_count`;
- if `old` is absent and `new` is already present in the expected count, return
  `NO_CHANGE` with an idempotency note;
- otherwise fail with expected and actual counts;
- on a count mismatch, report exact match line numbers or up to three bounded,
  similarity-ranked nearby snippets;
- verify the replacement count after writing.

### 13.5 `insert_before`

Fields:

- `path`: required existing text file;
- `anchor`: required non-empty exact text;
- `content`: required inserted text;
- `expected_count`: positive integer, default 1.

Behavior:

- preserve encoding and newline style;
- require the exact anchor count;
- insert immediately before each matched anchor;
- if the content is already immediately before each anchor, return
  `NO_CHANGE`;
- verify adjacency after writing.

### 13.6 `insert_after`

Fields and rules are the same as `insert_before`, but content is inserted
immediately after each matched anchor.

### 13.7 `delete_exact`

Fields:

- `path`: required existing text file;
- `text`: required non-empty exact text;
- `expected_count`: positive integer, default 1.

Behavior:

- require the exact count before deletion;
- remove only exact matches;
- verify absence after writing;
- on a first run, missing text is an error rather than an idempotent success;
- rerun idempotency is handled by the project registry at job level.

### 13.8 `apply_diff`

Fields:

- `diff`: required unified diff text;
- `strip`: integer 0, 1, or 2, default 1.

v0.1 rules:

- text files only;
- existing files only;
- no binary patches;
- no file deletion, rename, or mode change;
- all paths must pass normal workspace policy;
- every hunk must validate in a dry run before any file is written;
- invalid hunk counts report the hunk number plus declared and actual old/new
  counts;
- context mismatches report the hunk number, first mismatching source line,
  and bounded expected and actual previews;
- the implementation must not invoke a system shell or external `patch`
  command;
- all affected files are backed up before the first write;
- partial diff application is a failure followed by rollback.

## 14. Checks

Checks run through fixed built-in profiles or user-defined local profiles. A
job cannot provide an arbitrary shell command.

All subprocesses use argument arrays with `shell=False`.

### 14.1 Built-in profiles

#### `compileall`

```yaml
checks:
  - compileall:
      paths: ["src"]
      quiet: 1
```

Runs the current interpreter with `-m compileall`.

#### `pytest`

```yaml
checks:
  - pytest:
      paths: ["tests/test_clients.py"]
      args: ["-q"]
      timeout_seconds: 300
```

Only a documented allowlist of pytest arguments is accepted in v0.1.

#### `unittest`

```yaml
checks:
  - unittest:
      discover: "tests"
      pattern: "test_*.py"
```

Runs the current interpreter with `-m unittest`.

#### `django_check`

```yaml
checks:
  - django_check:
      manage_py: "manage.py"
```

Runs the current interpreter with `manage.py check`.

#### `django_migrations_check`

```yaml
checks:
  - django_migrations_check:
      manage_py: "manage.py"
```

Runs `manage.py makemigrations --check --dry-run`.

#### `django_test`

```yaml
checks:
  - django_test:
      manage_py: "manage.py"
      labels: ["clients.tests"]
```

#### `import_check`

```yaml
checks:
  - import_check:
      modules: ["patchshuttle", "patchshuttle.cli"]
```

Modules must match a conservative dotted-identifier pattern. The check does not
accept arbitrary Python expressions.

### 14.2 User-defined profiles

Users may define additional profiles in `patchshuttle.toml`. The executable and
base arguments live only in local configuration, not in an AI job.

Conceptual example:

```toml
[checks.profiles.manager_tests]
argv = ["{python}", "manage.py", "test"]
timeout_seconds = 900
allow_job_args = false
```

A job may then request:

```yaml
checks:
  - profile:
      name: manager_tests
```

The patch file cannot create or modify a local profile.

### 14.3 Check execution

For a patch job:

1. run all requested checks after actions;
2. if they pass, run isort and Black when applicable;
3. rerun the same checks after formatting;
4. fail and roll back on a non-zero exit code or timeout.

For a verify job, checks run once and no formatter is invoked.

## 15. Execution lifecycle

### 15.1 Audit job

```text
LOAD
-> VALIDATE
-> VERIFY PROJECT ID
-> APPLY POLICY
-> EXECUTE READ-ONLY ACTIONS
-> WRITE LOG
-> ARCHIVE JOB COPY
```

### 15.2 Verify job

```text
LOAD
-> VALIDATE
-> VERIFY PROJECT ID
-> APPLY POLICY
-> SHOW PLAN
-> CONFIRM
-> RUN CHECKS
-> WRITE LOG
-> ARCHIVE JOB COPY
```

### 15.3 Patch job

```text
LOAD
-> VALIDATE
-> VERIFY PROJECT ID
-> CHECK REGISTRY
-> APPLY POLICY
-> PLAN ALL ACTIONS
-> SHOW PLAN
-> CONFIRM
-> ACQUIRE WORKSPACE LOCK
-> REVALIDATE PLAN FINGERPRINTS
-> CAPTURE BASELINE
-> CREATE BACKUP MANIFEST
-> APPLY ACTIONS
-> VERIFY ACTION POST-STATES
-> RUN OPTIONAL HTML LINT
-> RUN INITIAL CHECKS
-> RUN ISORT
-> RUN BLACK
-> RUN FINAL CHECKS
-> COMPARE WORKSPACE STATE
-> WRITE FINAL STATUS
-> ARCHIVE JOB COPY
-> RELEASE LOCK
```

Any failure after backup creation enters rollback unless `--keep-changes` was
explicitly accepted.

## 16. Planning and approval

`patchshuttle plan JOB.psh.yaml` performs all validation and read-only planning
without creating backups or writing project files. Adding `--diff` displays a
bounded unified preview of the final resolved bytes.

Before executing a patch, the CLI displays at minimum:

```text
Project ID
Job ID and hash
Job kind
Files to create
Files to modify
Directories to create
Requested checks
Formatting scope
HTML lint scope
Quality preflight results
Protected-path result
Backup destination
Automatic rollback policy
```

The default prompt is:

```text
Apply this job? [y/N]
```

`--yes` is available for explicit automation. `--keep-changes` requires a
second explicit confirmation unless used together with `--yes`.

Audit jobs do not require confirmation because they are read-only. Verify jobs
require confirmation because they execute project code.

## 17. Transaction, backup, and rollback

### 17.1 Backup location

```text
patches/backups/<JOB_ID>/<RUN_TIMESTAMP>/
```

Each backup contains:

- a JSON manifest;
- the normalized job hash;
- original copies of every existing declared target file;
- an `ABSENT` record for every file or directory created by the job;
- original SHA-256 hashes;
- detected encoding and newline style;
- file mode where supported;
- action order;
- formatter targets;
- HTML linter targets;
- run metadata.

### 17.2 Atomic writes

File changes are written to a temporary file in the same directory, flushed,
and atomically replaced where supported by the operating system.

### 17.3 Rollback behavior

Rollback:

- restores declared modified files from backup;
- removes files created by the job;
- removes directories created by the job only when empty;
- does not use `git reset` or `git checkout`;
- does not delete logs, archived jobs, or backup data;
- updates the project registry;
- records its own result in the run log.

If rollback fails, PatchShuttle preserves the backup, reports every unresolved
path, returns `ROLLBACK_FAILED`, and does not claim restoration succeeded.

When the user explicitly accepts `--keep-changes`, automatic rollback is
skipped for that patch attempt. A failure after a declared change is published
records `CHANGES_KEPT` in the backup manifest and
`SKIPPED_CHANGES_KEPT` in the log and registry. A failure before any declared
change is published records `SKIPPED_NO_CHANGES`. Local policy may disable this
mode with `allow_keep_changes = false`.

### 17.4 Transaction boundary

The guaranteed transaction boundary is limited to files declared by change
actions and files changed by PatchShuttle's formatter step. The HTML linter is
lint-only; PatchShuttle verifies that it did not change a declared transaction
file.

External checks execute project code. They may create caches or modify files
outside the declared transaction. PatchShuttle records a before-and-after
workspace inventory and reports unexpected changes, but v0.1 does not promise
to restore arbitrary external side effects.

## 18. Formatting

Formatting is local policy, not an AI-job field.

Default patch behavior:

1. collect `.py` files created or modified by successful actions;
2. run the requested checks;
3. run isort on those files;
4. run Black on those files;
5. run the same checks again.

Rules:

- formatters never target the entire repository by default;
- non-Python jobs skip formatting with a recorded status;
- formatter availability is checked during preflight;
- Python source encoding is detected with the PEP 263 mechanism;
- final planned Python content must be accepted by isort and Black before
  confirmation and before any transaction write;
- formatter failure triggers rollback;
- formatter output and resulting file hashes are logged;
- AI jobs cannot change formatter order or scope.

Black and isort are required package dependencies in v0.1 so a normal
`pip install patchshuttle` provides the default workflow without an additional
installation step.

### 18.1 Optional HTML linting

HTML linting is local policy, not an AI-job field. It is disabled by default.
When enabled, PatchShuttle:

1. selects only created or modified files whose suffix is `.html`, using
   case-insensitive suffix matching;
2. requires the locally installed `djlint` module;
3. sends final planned bytes to djLint through stdin from an isolated temporary
   configuration root during read-only planning;
4. after applying actions, sends approved final bytes through stdin and runs
   djLint once per approved path in lint-only mode with a fixed argument array
   and `shell=False`;
5. stops after the first failure, timeout, or launch error and enters the
   normal rollback path;
6. verifies that the linter did not modify transaction files;
7. records bounded stdout, stderr, exit status, duration, profile, and path.

The optional `html` package extra installs `djlint>=1.44,<2`. PatchShuttle does
not install it automatically and never reformats HTML in this workflow.
Project `pyproject.toml`, `djlint.toml`, and `.djlintrc` files are not consulted
for this stage, so a change job cannot weaken local PatchShuttle lint policy.

## 19. Workspace protection

### 19.1 Built-in restrictions

PatchShuttle change actions must reject:

- absolute paths;
- parent traversal;
- protected paths;
- symbolic-link targets or symbolic-link parents;
- device files, sockets, and named pipes;
- binary files;
- oversized jobs or files;
- concurrent patch runs in the same workspace;
- a job created for another project ID;
- an already completed job with conflicting content.

### 19.2 Check-process warning

PatchShuttle must display and log this meaning before executing checks:

```text
Project checks execute local project code. PatchShuttle is not an OS sandbox.
Review the job and changed files before continuing.
```

### 19.3 Environment and secrets

Subprocess checks inherit the user's process environment unless a user-defined
profile restricts it. PatchShuttle overrides `PYTHONPYCACHEPREFIX` with a fresh
temporary directory for each check and removes that directory afterward, so
Python bytecode generated by checks stays outside the workspace. PatchShuttle
does not log environment-variable values.

Log redaction is best-effort. It searches for common token, password, API-key,
authorization-header, and private-key patterns. PatchShuttle must not describe
redaction as a guarantee that a log contains no secrets.

## 20. Registry and job archives

`patches/state/registry.json` stores only project-local operational state:

- project ID;
- job ID;
- normalized job hash;
- job kind;
- first and latest run timestamps;
- latest result;
- backup reference;
- rollback state;
- archived job-copy path.

Registry writes are atomic and protected by `patches/state/run.lock`.

The source job remains unchanged in `patches/inbox`. After every run,
PatchShuttle stores an exact archival copy in:

```text
patches/applied/
```

or:

```text
patches/failed/
```

Archive filenames include job ID, timestamp, and a short job hash.

## 21. Logs

### 21.1 Filename

```text
log_YYYY_MM_DD_HH_MM_SS_JOB_ID.log
```

Examples:

```text
log_2026_08_06_15_42_10_PATCH-001.log
log_2026_08_06_15_43_02_AUDIT-001.log
log_2026_08_06_15_44_17_INIT.log
```

The filename uses the configured local timezone. The header includes an ISO
8601 timestamp with UTC offset. If a filename collision occurs, PatchShuttle
adds a numeric suffix.

### 21.2 Encoding and sections

Logs are UTF-8 plain text. Standard sections are:

```text
HEADER
WORKSPACE
JOB
PLAN
AUDIT
BACKUP
ACTIONS
LINT_HTML
INITIAL_CHECKS
FORMAT_ISORT
FORMAT_BLACK
FINAL_CHECKS
WORKSPACE_COMPARISON
ROLLBACK
SUMMARY
PATCHSHUTTLE_AI_HANDOFF
```

For v0.1, all standard sections are present in their fixed order. An irrelevant
section contains the single value `NOT_APPLICABLE`. This makes logs predictable
for both people and AI consumers.

Validation and planning failures that occur after a workspace is resolved use
a smaller early-attempt format. The filename label is `VALIDATION_FAILED` or
`PLAN_FAILED`, and the log contains attempt metadata plus stable `SUMMARY` and
`PATCHSHUTTLE_AI_HANDOFF` sections. Invalid source is not archived as a valid
job, no registry entry is created, and no project change or backup is reported.
If writing the failure log also fails, the CLI preserves the primary failure
and reports the operational-recording failure separately.

CLI messages, logs, generated protocol files, and `AI_GUIDE.md` use English in
v0.1. Localization is outside the first-release scope.

### 21.3 Action record

Each action record includes:

```text
action_id
action_type
path or scope
status
started_at
duration_ms
expected
actual
details
```

### 21.4 Check record

Each check record includes:

```text
check_id
profile
argument summary
working directory
timeout
exit code
duration_ms
stdout
stderr
truncation status
```

### 21.5 Summary

The summary includes:

```text
result
failure_stage
exit_code
changed_files
created_files
created_directories
checks_passed
html_lint_status
formatting_status
rollback_status
log_path
next_recommended_step
```

### 21.6 AI handoff block

Every log ends with a compact stable block:

```text
=== PATCHSHUTTLE_AI_HANDOFF ===
protocol: 1
project_id: PSH-8F41C2A73D905E61
job_id: PATCH-001
job_hash: 12ab34cd
kind: patch
result: ROLLED_BACK
failure_stage: INITIAL_CHECKS
failure_code: CHECK_FAILED
failed_item: check_001
rollback: SUCCESS
available_job_kinds: [audit, patch, verify]
available_audit_actions: [tree, read, search, find_files, file_info, hash, git_status, environment]
available_change_actions: [create_directory, create_file, replace_exact, insert_before, insert_after, delete_exact, apply_diff]
available_checks: [compileall, pytest, unittest, django_check, django_migrations_check, django_test, import_check, profile]
next_expected_response: corrected_patch_or_audit
=== END_PATCHSHUTTLE_AI_HANDOFF ===
```

## 22. Snapshot and handoff

### 22.1 Snapshot

```bash
patchshuttle snapshot
```

Creates a read-only timestamped log containing:

- project ID;
- PatchShuttle and Python versions;
- a bounded project tree;
- file paths, sizes, and SHA-256 hashes;
- Git status if available;
- recent job IDs and results;
- available actions and checks;
- ignored and protected-path summaries.

It does not include all source-file contents.

### 22.2 Handoff

```bash
patchshuttle handoff
```

Creates one upload-friendly `.log` file containing:

- a compact AI instruction;
- project ID and protocol version;
- available capabilities;
- the latest run summary and AI handoff block;
- a bounded project tree;
- recent job history;
- clear instructions to return one `.psh.yaml` file.

Source excerpts are included only when produced by an explicit audit job.

## 23. CLI contract

```text
patchshuttle [--workspace PATH] COMMAND [ARGS]
patchshuttle init [--new-project]
patchshuttle validate JOB.psh.yaml
patchshuttle plan JOB.psh.yaml [--diff]
patchshuttle audit JOB.psh.yaml
patchshuttle verify JOB.psh.yaml [--yes]
patchshuttle run JOB.psh.yaml [--yes] [--keep-changes]
patchshuttle status [JOB_ID]
patchshuttle rollback JOB_ID [--yes]
patchshuttle snapshot
patchshuttle handoff
patchshuttle logs --last
patchshuttle capabilities
patchshuttle schema
patchshuttle explain TOPIC
patchshuttle version
```

Command behavior:

- `validate` parses and validates without reading target files beyond workspace
  identity and configuration;
- `plan` performs all in-memory planning and policy validation without writing
  project source; a failed attempt may write its managed failure log;
- `audit` requires `kind: audit`;
- `verify` requires `kind: verify`;
- `run` accepts all job kinds and is the universal executor;
- `status` reads registry and recent logs;
- `rollback` uses an existing backup manifest;
- `logs --last` prints the path to the latest log;
- `capabilities`, `schema`, and `explain` inspect the installed contract without
  requiring a workspace;
- `--workspace` applies to workspace-aware commands and must precede the
  command name;
- all commands support `--help` and `--version` where appropriate.

## 24. Public Python API

The public API uses immutable typed job, action, check, plan, and result models.

Conceptual usage:

```python
from patchshuttle import Job, plan_job, execute_plan
from patchshuttle.actions import create_file, replace_exact
from patchshuttle.checks import compileall

job = Job(
    protocol=1,
    project_id="PSH-8F41C2A73D905E61",
    id="PATCH-001",
    kind="patch",
    actions=[
        create_file(
            path="src/example/greeting.py",
            content="def greet(name: str) -> str:\n    return f'Hello, {name}!'\n",
        ),
    ],
    checks=[compileall(paths=["src"])],
)

plan = plan_job(job, workspace=".")
result = execute_plan(plan, approved=True)
```

Required public names for v0.1:

- `Job`;
- `Plan`;
- `RunResult`;
- `Workspace`;
- `Policy`;
- `load_job`;
- `validate_job`;
- `plan_job`;
- `execute_plan`;
- audit and change action constructors;
- check constructors.

Public constructors create declarative models. They do not modify files until
an approved plan is executed.

YAML remains the recommended format for jobs returned directly by third-party
AI services. A Python program importing PatchShuttle is not treated as a
security boundary because arbitrary Python code can execute outside the API.

## 26. Process exit codes

| Exit code | Meaning |
| ---: | --- |
| 0 | Completed, no change, or already applied. |
| 1 | Unexpected internal error. |
| 2 | CLI usage, YAML parsing, or schema validation error. |
| 3 | Workspace, project ID, or job ID conflict. |
| 4 | Policy block or user declined. |
| 5 | Planning or action failure. |
| 6 | Initial or final check failure. |
| 7 | isort or Black failure. |
| 8 | Rollback failure. |
| 9 | Required dependency or local check profile unavailable. |

The root-cause exit code is retained when rollback succeeds. Exit code 8 is
used only when rollback itself fails.

## 32. Acceptance criteria for v0.1.0

PatchShuttle v0.1.0 is ready when all of the following are demonstrated:

1. `pip install patchshuttle` installs the package and CLI in a clean supported
   environment.
2. `patchshuttle init` initializes an existing project without overwriting
   user files.
3. `patchshuttle init --new-project` initializes an empty workspace.
4. An AI-style audit job produces a bounded, readable log without changing the
   project.
5. A patch job creates and modifies files only after a valid plan and user
   approval.
6. All v0.1 change actions are guarded, logged, and covered by tests.
7. Successful initial checks are followed by isort, Black, and final checks for
   changed Python files.
8. An action, check, or formatter failure restores all declared transaction
   files and records the root cause.
9. A rollback failure is reported without a false success claim.
10. A repeated successful job does not duplicate its changes.
11. A conflicting job ID is rejected.
12. Path traversal, protected targets, and symbolic-link escapes are rejected.
13. PatchShuttle works without Git and adds Git metadata when Git is available.
14. A new project can be built through at least three successive jobs from an
    initially empty directory.
15. `snapshot` and `handoff` produce upload-friendly logs with the correct
    project ID, status, and capabilities.
16. The public Python API and YAML adapter produce equivalent internal jobs and
    execution plans.
17. Required Windows and Ubuntu CI targets pass.
18. TestPyPI installation succeeds before the production PyPI release.

### Current qualification record

required GitHub-hosted matrix closes criterion 17, the successful TestPyPI
workflow closes criterion 18, and a clean installation from production PyPI
closes criterion 1. All listed v0.1.0 acceptance criteria therefore have
recorded evidence for the current implementation. Version `0.1.0a2` remains an
alpha pre-release; no stable `0.1.0` release has been published. The separate

not extend to every action or intentional failure and rollback path.

## 33. Fixed decisions for implementation

The following decisions are considered fixed for the first implementation
unless this specification is explicitly revised:

- distribution, import, and CLI name: `patchshuttle`;
- canonical AI job format: `.psh.yaml`;
- protocol version: `1`;
- job kinds: `audit`, `patch`, `verify`;
- local policy cannot be weakened by an AI job;
- normal execution is interactive;
- automatic backups and rollback are enabled;
- isort runs before Black;
- checks run before and after formatting;
- only changed Python files are formatted;
- optional HTML linting is local policy, changed-file-only, and lint-only;
- no automatic dependency installation;
- no arbitrary shell supplied by a job;
- no automatic Git commits;
- new and existing projects use the same engine;
- logs are plain UTF-8 text with timestamped names and an AI handoff block;
- implementation begins with tests for the contract before completing the
  execution engine.
